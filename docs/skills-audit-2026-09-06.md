**文章依据与适用范围**

已通过浏览器阅读 Eric Provencher 的
[Rethinking skills and prompts for GPT-6 Astra](https://x.com/pvncher/status/2095991462416490862)
原文。文章强调简洁准确的技能发现描述、按需加载细节、减少固定步骤，以及把
审批边界和完成条件写清楚。关于 Astra 比旧模型更自主或更谨慎的比较，是作者的
使用判断；本轮没有进行模型对比实验，不能把这些判断直接推广到所有宿主和模型。

[OpenAI 的 Build skills 文档](https://learn.chatgpt.com/docs/build-skills)
也说明，技能名称和描述先用于发现，完整指令和资源随后按需加载；技能较多时描述
可能被缩短，因此应把决定是否触发的信息放在前面。本轮另参照当前内置
`skill-creator` 的规则，区分必要约束、默认建议和可以删去的重复指导。

对本仓库的应用：保留事实保护、原生可编辑输出、构建与运行验证的区别，以及
实际发布授权；减少与当前请求无关的流程。仓库面向多个平台，不应仅凭模型升级
就撤掉发布检查，或假定所有使用者都运行 Astra。

**1. 优先处理安装版本与源码版本的差异**

本次会话提供的技能目录仍引用 `skillsplace` 缓存中的 `0.6.3`。只读检查确认
`dev-tools`、`faculty-tools`、`writing-tools` 的对应缓存 manifest 也是 `0.6.3`。
其中 `humanizer`、`rewrite-for-clarity`、`summarize-material`、
`meeting-synthesizer` 的安装内容与当前源码不同。

这说明发布成功与本次会话使用最新版是两件事；不能根据源码已经改善，就假定日常
调用获得了改善。此结论只覆盖本次会话和检查到的缓存，不代表其他客户端的状态。

建议先通过正常插件更新机制核对安装版本，再确认新会话能发现新版描述和英文
写作参考。若更新仍停在旧版，再追查市场引用或客户端缓存；不要直接修改生成缓存，
也不要未经核实把问题归因于发布流程。

**2. 高优先：把任务范围与审批边界写成一致的条件**

| 位置 | 现有规则和风险 | 最小调整 |

条件表达审查边界，可以保留。`faculty-email` 和 `pr-description` 的草稿职责也有

**3. 高优先：演示文稿的创建、局部编辑、审查和导出需要不同流程**

[presentation-tool](../plugins/presentation-tools/skills/presentation-tool/SKILL.md)
第 25–36 行和 [slidev-slides](../plugins/presentation-tools/skills/slidev-slides/SKILL.md)
第 21–31 行把提纲、新建内容和验证串成统一步骤，但描述同时覆盖编辑和审查。
例如“只修改第 3 页标题并导出”，不需要重新确定听众、重写全稿提纲或检查全场演讲时长。

建议在现有入口内加入简短的任务分支，无须再拆技能：

- 新建：明确交付格式与约束，必要时设计提纲，完成制作和渲染。
- 局部编辑：读取相关页、模板和依赖，保留未请求变更的结构，验证受影响页。
  全局主题、字体或布局改变时才扩大视觉检查范围。
- 审查：返回问题和依据；不因技能中存在制作步骤而修改文件。
- 导出：复用现有源文件与命令，验证目标产物，不额外重新设计。

同时明确：修复本次操作引入的构建或排版问题，再检查受影响部分；工具不可用时
按已有 fallback 如实说明。原生 PPTX 可编辑性、CJK 字体、静态导出语义和视觉验证
是实际约束，应保留。[format-workflows.md](../plugins/presentation-tools/skills/presentation-tool/references/format-workflows.md)
已有的“产物生成”和“布局已验证”区分也应保留。

**4. 高优先：Humanizer 缩窄诊断加载条件，保留信达雅标准**

[humanizer](../plugins/writing-tools/skills/humanizer/SKILL.md) 第 43–47 行要求对
robotic/generic style 问题读取 `style-diagnostics.md`，而这本来就是该技能的主要
触发原因。[诊断参考](../plugins/writing-tools/skills/humanizer/references/style-diagnostics.md)
第 3–5 行还覆盖 stiff、AI-like 等，因而这个条件几乎不能筛掉普通调用。

按现有加载规则，一个简单英文润色也可能读取 63 行入口、66 行英文指南和 87 行
诊断，共 216 行；中文对应 232 行。这里计算的是文本路径长度，不是本轮观测到的
实际调用日志。学术编辑还会增加 61 行参考。

最小调整是保留中英文指南，先缩窄诊断参考的触发：只在确有跨段推理、指代、衔接
问题，或普通改写仍不能解决的问题时加载。短句“写得更自然”不应自动加载全部诊断。
随后可合并入口、语言指南、诊断中重复的衔接检查，但不能以减行数为目标删掉：

- 信优先于达和雅，保留数字、承诺、证据强度和作者意图；
- 中文语域、简繁与地区习惯，英文自然搭配与地区一致性；
- 区分真实转折、原因、先后与话题切换；
- 保留必要连接词和已经自然的句子，不制造禁词清单；
- 不通过虚构前提来掩盖原文的逻辑缺口。

这些是上一轮用户明确要求且已有实例支撑的规范。本轮精简的是重复读取，不能据
文章的总体建议撤销这些写作要求。

**6. 低优先：描述和通用措辞可进一步压缩，但不是当前主要故障**

目前描述长度没有达到严重膨胀的程度，也没有发现要求凡是沾边就调用的强制触发词。
最容易精简的是 `faculty-email` 的收件人枚举、`feedback-writer` 的作品类型枚举，
以及描述中属于执行阶段的细节。需要区分相邻技能时，仍保留关键边界。

例如 `faculty-email` 可收敛为：

> Draft or revise university emails from supplied context and policy. Use for send-ready drafts.

不要另设一个机械字符上限，也不要为减少上下文而批量关闭隐式调用。先检查描述
压缩后是否仍能正确区分相近任务。

`release-readiness`、`repo-boundary-review` 等入口的三行通用行文指导可以压成一句。
但不要为几句话新增共享文件和强制加载依赖。尤其
[DEVELOPMENT.md](../DEVELOPMENT.md) 第 264–265 行允许把参考放到插件级，
而 [镜像脚本](../scripts/sync_hermes_tap.py) 只复制技能目录；今后去重时必须保证
Hermes 单技能安装仍能取得参考。这是维护规则中的潜在风险，本轮未发现现有资源
已经因此丢失。

**7. 修改后的验收应覆盖提前停止和任务规模，而不仅是路由**

[现有评估文件](../evals/skill-routing.json) 包含 60 条基础路由提示和 23 个行为场景。
23 个场景的预期主技能分布为：Humanizer 13、clarity 2、summary 3、meeting 2、
presentation-tool 3，共覆盖 5 个技能。其余 15 个技能有基础路由提示，但没有同等
详细的行为场景。

[验证器](../scripts/validate_plugins.py) 第 307 行已正确说明它只检查场景结构，
不会验证实际输出。此前独立执行的记录有价值，但它没有覆盖本轮发现的教学、
调试和已授权组合任务，也没有证明技能相对模型原生能力的增益。

建议沿用现有文件和人工观察流程，只补与实际修改对应的用例：

| 场景 | 要观察的结果 |
| --- | --- |
| “只解释失败原因”与“帮我把构建跑通” | 前者不改文件；后者完成授权内的修复和相关验证，不再重复询问修复权限。 |
| 已授权提交或发布中的消息生成、readiness 步骤 | 局部技能完成后继续外层任务；对没有授权的外部写入仍保持边界。用隔离仓库或模拟服务观察，不触碰真实发布。 |
| 改一页标题、只审查、直接导出 | 遵守对应任务范围，不重写全稿；验证实际受影响产物。 |
| 80 字教师简介与完整教学陈述 | 输出结构随体裁变化，事实一致；不强加反思段落。 |
| 含 6 个既定目标的课程与短活动 | 保留既定目标，不因为固定数量限制而删改课程要求。 |
| 提出新 rubric 与转述已批准 rubric | 前者明确是建议，后者完整保留已批准规则。 |
| 单句中英文润色与跨段逻辑修订 | 事实和流畅度达标；前者不自动读取诊断大全，后者读取所需参考。 |

对最通用的写作、决策或规划条款，可用少量代表任务比较“不加载技能 / 当前技能 /
精简技能”。先看事实、范围、完成度和成稿质量，再看额外读取与交互次数；不要把
字数少当成效果好。若实际使用多个模型，再覆盖常用模型，不先搭建评估平台。
